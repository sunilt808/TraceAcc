This document is the authoritative Production Readiness Review (PRR) for the
TraceAcc Money Muling Detection System. It is structured as a mandatory reading
for any engineer joining this project or a manager evaluating it.

────────────────────────────────────────────────────────────────────────────────
1. EXECUTIVE SUMMARY
────────────────────────────────────────────────────────────────────────────────

TraceAcc is a full-stack Anti-Money Laundering (AML) detection platform that:
  1. Ingests CSV transaction data
  2. Builds an in-memory directed financial graph using NetworkX
  3. Runs 4 graph heuristic detectors (cycle, fan, layering, burst)
  4. Augments with 3 unsupervised ML anomaly detectors (Isolation Forest,
     Local Outlier Factor, DBSCAN)
  5. Computes weighted suspicion scores per account (0–100)
  6. Renders results on an interactive React/Cytoscape.js dashboard

The system is architecturally sound at the algorithm level but has critical
gaps in production infrastructure: synchronous blocking compute, no transaction
persistence, no background task queue, and misconfigured CORS for deployment.

2. ARCHITECTURE REVIEW
────────────────────────────────────────────────────────────────────────────────

2.1 Tier Structure
  ✓ Presentation: React + Vite SPA (port 5173)
  ✓ Application: FastAPI + Uvicorn (port 8000)
  ✓ Data: PostgreSQL/Supabase with SQLAlchemy ORM
  ✗ Missing: Message broker tier (Celery/Redis), caching layer (Redis)

2.2 Code Organization
  GOOD: Routes are split across api/routes/ (auth, audit, analysis, graph, cases)
  GOOD: Detection algorithms are isolated in detectors/ with single responsibility
  GOOD: Services (auth_service, audit_service) separate business logic from routes
  BAD:  main.py still contains the core /analyze endpoint (should be in api/routes/)
  BAD:  No repository pattern — services issue SQLAlchemy operations directly

2.3 Scalability Assessment: CRITICAL FAIL
  The /analyze endpoint runs CPU-bound NetworkX DFS and sklearn.fit() inside
  an async def coroutine. In Python's asyncio event loop, synchronous CPU work
  blocks all concurrent requests. One large CSV upload freezes the entire server.

  Load Test Estimate (theoretical):
    - 1 user, 1,000-row CSV: ~0.5s (acceptable)
    - 1 user, 10,000-row CSV: ~5s (marginal, other requests blocked)
    - 3 concurrent users, 10,000-row CSV each: server unresponsive for 15s+
    - 1 user, 50,000-row CSV: timeout, OOM risk, server crash

  Required Fix:
    Option A (quickest): run_in_executor with ThreadPoolExecutor
      result = await asyncio.get_event_loop().run_in_executor(
          None, run_analysis_sync, graph_data)
    Option B (production): Celery + Redis task queue

3. BACKEND (FastAPI & API DESIGN)
────────────────────────────────────────────────────────────────────────────────

3.1 Endpoint Inventory
  POST /analyze                - CSV upload + full analysis (BLOCKING — see §2.3)
  POST /sample-generator       - Synthetic dataset generation
  POST /auth/login             - JWT issuance
  POST /auth/register          - User registration
  GET  /auth/me                - Current user info
  GET  /audit/logs             - Paginated audit log
  GET  /audit/stats            - Login counts, failure counts
  GET  /analyze/jobs           - Analysis job history
  GET  /graph/*                - Graph-level API endpoints
  GET  /cases/*                - Case management endpoints

3.2 API Design Quality
  ✗ Missing: API versioning (/api/v1/ prefix). Breaking changes will break clients.
  ✗ Missing: Structured error responses. Returns {"error": str(e)} instead of
    HTTPException(status_code=422, detail={...})
  ✗ Missing: File size validation. Accepts unlimited file size → DoS vector.
  ✗ Missing: File type validation. Accepts any MIME type, not just text/csv.
  ✓ Good: JWT auth with Depends(get_current_user) on all protected endpoints.
  ✓ Good: CORS middleware configured (though needs production URL addition).

3.3 Logging
  ✓ Audit DB logging with event types, actions, statuses, duration_ms — excellent.
  ✗ Application-level Python logging missing. print() is used instead of
    logging.getLogger("trackacc"). No log rotation, no structured log format.
  ✗ No request ID correlation across logs (hard to trace multi-step failures).

3.4 Authentication
  ✓ JWT with bcrypt password hashing (passlib) — correct implementation.
  ✗ No refresh token mechanism. 120-minute access tokens expire with no renewal.
  ✗ No token blacklist/revocation. Compromised tokens are valid until expiry.
  ✗ No password complexity enforcement on /auth/register.
  ✗ No login rate limiting. Brute-force attack is unrestricted.

3.5 Performance Bottlenecks
  HIGH: detect_burst_activity — O(N×T) nested iteration over all nodes and all
        transactions. On 10,000 nodes × 100,000 transactions = 1 billion ops.
  MEDIUM: Cycle detector runs DFS with max_cycles=200. Deep recursive DFS on
          dense graphs can hit Python recursion limits.
  MEDIUM: ML anomaly detection (sklearn.fit) runs in the request thread.

4. DETECTION ALGORITHMS
────────────────────────────────────────────────────────────────────────────────

4.1 Cycle Detection (detectors/cycle.py) — Score: A-
  Correctness: Correct DFS with backtracking and visited tracking.
  Optimization: Lexicographic pruning avoids duplicate cycle reports.
  Gap: max_length=4 is hardcoded in main.py (now configurable in SettingsPage).
  Gap: Does not scale to graphs >10,000 edges without cycle count capping.

4.2 Fan-In/Fan-Out Detection (detectors/fan.py) — Score: B+
  Correctness: Correct degree-based hub identification with temporal windowing.
  Gap: Time window check uses a deque but scans forward linearly — O(T) per node.
  Gap: Threshold values (default 3) are arbitrary without empirical calibration.

4.3 Layering Chain Detection (detectors/layering.py) — Score: B
  Correctness: Traces shell chains through low-degree nodes effectively.
  Gap: min_chain_length=3 and max_degree=3 may miss longer or denser shell chains.
  Gap: The path deduplication logic may produce overlapping chains in dense graphs.

4.4 Burst Detection (detectors/burst.py) — Score: B-
  Correctness: Dormancy→surge pattern is correctly modeled.
  Gap: O(N×T) complexity is the primary performance bottleneck (see §3.5).
  Fix: Pre-index transactions per account in the graph object. O(N+T) → O(T).

4.5 ML Anomaly Detection (detectors/ml_anomaly.py) — Score: A
  Correctness: Excellent. Real feature matrix (11 features), StandardScaler,
               3 independent unsupervised models, combined scoring.
  Gap: Models are re-trained per request (no serialization/caching).
  Gap: contamination=0.1 (10% anomaly assumption) is arbitrary.
  Note: This is the most sophisticated component in the project.

4.6 Scoring Engine (detectors/score.py) — Score: B
  Correctness: Multi-heuristic weighted aggregation is architecturally correct.
  Gap: Weights (Cycle=40, Fan=25, Burst=25, Layering=20) are not empirically
       derived from a labeled dataset. They are intuition-based.
  Gap: ML anomaly scores are NOT yet integrated into the final suspicion score.

6. DATABASE (PostgreSQL / SQLAlchemy)
────────────────────────────────────────────────────────────────────────────────

6.1 Schema Reality Check
  CURRENT:
    users              — user accounts (correct)
    audit_logs         — event tracking (excellent, good indexes)

  MISSING FOR PRODUCTION:
    accounts           — discovered account entities from uploaded data
    transactions       — persisted financial transactions
    analysis_jobs      — job records with results JSON
    detected_rings     — fraud rings with membership lists
    fraud_cases        — analyst-managed investigation cases

  Without these tables, every analysis result is lost on page refresh.
  The /analyze/jobs endpoint exists but returns empty because nothing is persisted.

6.2 Index Strategy
  ✓ Composite indexes on audit_logs: (user_id, timestamp) and (event_type, event_action)
  ✗ AuditLog.details is TEXT, not JSONB. Cannot query details fields in SQL.
  ✗ No full-text search indexes for analysis results.

7. MACHINE LEARNING ASSESSMENT
────────────────────────────────────────────────────────────────────────────────

The system uses unsupervised ML correctly as a supplementary signal layer:

  WHAT'S REAL:
  - 3 independent models with different detection mechanisms (ensemble, density, clustering)
  - 11-dimensional feature vectors built from transaction graph structure
  - StandardScaler normalization preventing scale bias
  - Combined ML flag scoring

  WHAT'S MISSING:
  - No labeled ground truth dataset → can't compute precision/recall/F1
  - ML scores are computed but NOT merged into suspicion_score in score.py
  - Models are re-fit per request (~1-2s overhead) with no caching
  - No explainability (SHAP values) to tell analyst WHY an account was flagged

  PATH TO REAL ML:
  1. Build labeled dataset (even synthetic with known fraud patterns)
  2. Train XGBoost or GNN on structural features
  3. Calibrate scores against true positives
  4. Add SHAP explanation output per account

8. SECURITY REVIEW
────────────────────────────────────────────────────────────────────────────────

8.1 Critical Issues
  [CRITICAL] File upload has no size limit — DoS via large CSV is trivial.
    Fix: contents = await file.read(10 * 1024 * 1024)  # 10MB limit
  [HIGH]     JWT stored in localStorage — vulnerable to XSS token theft.
    Fix: Use HttpOnly, SameSite=Strict cookies.
  [HIGH]     No rate limiting on /auth/login — brute-force is unrestricted.
    Fix: SlowAPI or redis-based rate limiter at 5 attempts / minute.
  [MEDIUM]   No input sanitization on file.filename — though not used in SQL.
  [MEDIUM]   CORS allows all localhost ports — production URL must be added.

8.2 OWASP Top 10 Coverage
  A01 Broken Access Control:    ✓ JWT on all protected routes
  A02 Cryptographic Failures:   ✓ bcrypt for passwords
  A03 Injection:                ✓ ORM (no raw SQL), CSV parsed safely
  A04 Insecure Design:          ✗ No rate limiting, no file size limits
  A05 Security Misconfiguration: ✗ Broad CORS, print() exposes traces
  A06 Vulnerable Components:    ? Dependencies not audited (pip-audit needed)
  A07 Auth Failures:            ✗ No refresh token, no revocation
  A08 Data Integrity:           ✓ Input validated via Pydantic schemas
  A09 Logging:                  ✓ Audit log excellent; ✗ app logging missing
  A10 Server-Side Request Forgery: N/A (no external URL fetching)

12. FINAL VERDICT
────────────────────────────────────────────────────────────────────────────────

STRENGTHS:
  + 21 fraud detection modules — far beyond typical student projects
  + Real unsupervised ML (not toy sklearn usage)
  + Excellent audit logging with proper event structure
  + Production-quality UI with Cytoscape.js graph visualization
  + Correct mathematical modeling of AML patterns

WEAKNESSES:
  - Zero transaction data persistence (core business data evaporates)
  - Synchronous blocking CPU work inside async FastAPI handlers
  - No background workers, no task queue
  - No automated tests of any kind

WOULD YOU DEPLOY THIS TO A BANK?
  No. The blocking compute will crash under concurrent load, and the complete
  absence of transaction persistence means the system has no memory. It is a
  sophisticated demo, not a production platform.

WOULD THIS GET A STRONG INTERVIEW CONVERSATION?
  Yes — if positioned correctly as a prototype with a clear production roadmap.
  The algorithmic depth (DFS cycle pruning, LOF density anomaly, layering chain
  tracing) gives an interviewer many meaningful threads to pull.
