SECTION A: THE GOOD — WHAT GENUINELY IMPRESSES ME
================================================================================

1. THE DETECTION ALGORITHM SUITE IS GENUINELY DIVERSE AND THOUGHTFUL
   ─────────────────────────────────────────────────────────────────
   Most student fraud projects implement ONE algorithm (usually just cycle
   detection) and call it done. This project implements TWENTY-ONE distinct
   detector modules. That's not just quantity — the selection is architecturally
   coherent:

   - Cycle detection handles circular routing (most common money ring pattern)
   - Fan-In/Out covers aggregation/disbursement hubs (textbook AML)
   - Layering chains catch shell account pass-throughs (advanced AML pattern)
   - Burst detection catches dormancy → sudden activity (mule activation)
   - ML anomaly detection (Isolation Forest + LOF + DBSCAN) is genuinely
     sophisticated for an academic project

   The lexicographic pruning in cycle.py (preventing A→B→C→A, B→C→A→B,
   C→A→B→C from being triple-reported) shows actual algorithmic thinking,
   not just calling a library.

2. THE ML INTEGRATION IS REAL, NOT FAKE
   ─────────────────────────────────────
   ml_anomaly.py does real unsupervised ML:
   - 11-feature behavioral vector per account
   - StandardScaler normalization before fitting
   - Three independent models with different detection mechanisms
   - Combined flagging with score proportional to model agreement
   This is not a dummy sklearn.fit() call. The feature engineering
   (pass_through_ratio, net_flow, activity_span_hours) is domain-correct.

3. AUDIT LOGGING IS A PRODUCTION-QUALITY FEATURE
   ───────────────────────────────────────────────
   The audit_service with EventType/EventAction/EventStatus enums and
   composite DB indexes on (user_id, timestamp) and (event_type, event_action)
   is something most senior engineers forget to add. It shows security maturity.

4. THE FRONTEND IS GENUINELY BEAUTIFUL
   ─────────────────────────────────────
   The landing page with 3D perspective grid, floating orbs, Cytoscape live
   graph demo, 3D card tilt on mouse hover, and glassmorphic LoginCard are
   well above average for a student project frontend. The sidebar navigation
   with 14 distinct protected routes shows a real app architecture, not just
   a landing page wrapper.

5. THE SYNTHETIC DATASET GENERATOR IS USEFUL
   ───────────────────────────────────────────
   Having a sample generator with fraud-pattern presets (Small Cycle Ring,
   Fan-In/Out Hub, Enterprise Mix) means the system is self-contained for
   demos and testing. This shows product thinking.

SECTION B: CRITICAL PROBLEMS I SEE
================================================================================

1. THE ANALYZE ENDPOINT IS A TICKING TIME BOMB
   ──────────────────────────────────────────────
   main.py line 56-158 runs the entire pipeline — CSV decode, graph build,
   DFS cycle search, burst detection, ML inference — inside an async def.
   async def in FastAPI means "I promise I won't block the event loop."
   But NetworkX DFS and sklearn fitting ARE blocking. On a 50,000-row CSV
   this will freeze the server for 30+ seconds and kill all concurrent users.

   The fix is straightforward:
     loop = asyncio.get_event_loop()
     result = await loop.run_in_executor(None, run_full_analysis, graph)
   Or use BackgroundTasks + polling, or Celery.

2. SCORE WEIGHTS ARE COMPLETELY ARBITRARY
   ──────────────────────────────────────
   Cycle=40, Fan=25, Burst=25, Layering=20 — these numbers are not from
   FATF guidelines, not from Basel III standards, not from any calibrated
   training set. They were chosen by intuition.

   For a demo this is fine. But presented as "suspicion score" to an analyst,
   an account with score 40 (only a cycle) might be LESS suspicious than one
   with score 25 (burst activation after 6-month dormancy). The weights need
   empirical calibration against labeled fraud datasets, or at minimum should
   be configurable per deployment (the Settings page is a good start).

3. ZERO DATA PERSISTENCE FOR TRANSACTIONS
   ─────────────────────────────────────────
   Every analysis is stateless. Upload CSV → analyze → results returned →
   everything discarded. The analyst cannot:
   - Look up a previous analysis without re-uploading
   - Compare two time periods
   - Track whether a flagged account appears in future uploads
   - Build a case against an account over time

   The database has users + audit_logs. That's it. The entire business value
   (detected rings, suspicious accounts) is thrown away after each response.

4. THE FRONTEND ROUTES /graph-viewer, /communities, /risk-map, /timeline,
   /statistics, /reports, /cases APPEAR TO BE STUB PAGES
   ────────────────────────────────────────────────────────
   Looking at the component list: GraphViewer, CommunitiesPage, RiskMapPage,
   TimelinePage, StatisticsPage, ReportsPage, CasesPage. These are imported
   and routed in App.jsx. But I see no backend API endpoints for communities,
   risk-map, timeline, or statistics beyond the main /analyze response.
   These pages may be empty scaffolds. If they are, they should not appear
   in a demo as working features.

5. CORS IS TOO BROAD FOR DEPLOYMENT
   ──────────────────────────────────
   allow_origin_regex="https?://(localhost|127\\.0\\.0\\.1)(:\\d+)?"
   This allows all localhost ports. In production the Vercel frontend URL
   must be explicitly allowlisted, otherwise the API will reject requests
   from the deployed frontend.

SECTION C: SPECIFIC THINGS I WOULD FIX RIGHT NOW
================================================================================

Priority 1 (20 minutes of work):
  - Wrap the analyze pipeline in run_in_executor to unblock the event loop
  - Add MAX_UPLOAD_SIZE = 10 * 1024 * 1024 check before reading file.read()
  - Add CORS origin for the production Vercel URL

Priority 2 (1-2 hours of work):
  - Create analysis_jobs table in the DB — store job id, filename, results JSON,
    user_id, created_at. Return job_id immediately. Load results from DB on revisit.
  - Connect /overview page to the job history endpoint (the endpoint exists
    at /analyze/jobs — the DB just needs to store something)

Priority 3 (for production):
  - Replace print() with logger = logging.getLogger("trackacc")
  - Add Celery task queue for graph analysis
  - Add /api/v1/ prefix to all routes
